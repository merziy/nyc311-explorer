# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

NYC 311 Explorer: a "chat with your data" app over NYC's 311 service request dataset. A Flask API backed by Postgres (`backend/`), an ingestion script that pulls real data from NYC's Socrata API, a `POST /api/ask` NL→filter endpoint (Claude tool-use), and a Vue 3 frontend (`frontend/`) all exist and work end to end.

## Commands

Local Postgres (dev):
```
docker compose up -d
```
Starts Postgres 16 on `localhost:5432` with user/password/db all `nyc311` (see `docker-compose.yml`).

Backend setup:
```
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp ../.env.example .env   # then fill in ANTHROPIC_API_KEY and SOCRATA_APP_TOKEN
```
`DATABASE_URL` in `.env.example` already matches the docker-compose credentials. `SOCRATA_APP_TOKEN` comes from a free account at data.cityofnewyork.us (Profile → Developer Settings, or the API panel on the dataset's own page) — ingestion works without one but at a much lower rate limit.

Run the backend:
```
cd backend
FLASK_APP=app.main .venv/bin/flask run --port 8000
```

Run the frontend (separate terminal):
```
cd frontend
npm install
npm run dev
```
Opens on `http://localhost:5173`. The backend must be running on `:8000` — CORS is only opened for that specific origin (see Architecture below), not wildcarded.

Migrations (Flask-Migrate / Alembic, config lives in `backend/migrations/`):
```
cd backend
FLASK_APP=app.main .venv/bin/flask db migrate -m "description"   # autogenerate from models.py
FLASK_APP=app.main .venv/bin/flask db upgrade                    # apply
FLASK_APP=app.main .venv/bin/flask db downgrade                  # roll back one revision
```
Always read the autogenerated migration in `backend/migrations/versions/` before applying it — Alembic's autogenerate misses some things (e.g. it won't infer `CHECK` constraints unless the model explicitly declares them, as `models.py` does for `borough`).

Ingestion (pulls real 311 data from Socrata into `complaints`):
```
cd backend
.venv/bin/python -m scripts.ingest_311
```
Safe to re-run or interrupt — see Architecture below for the checkpoint/retry behavior.

No test suite, linter, or CI config exists yet.

## Architecture

**App factory pattern.** `backend/app/__init__.py` defines `create_app()`, which builds and configures the Flask app; `backend/app/main.py` just calls it (`app = create_app()`) and is the entrypoint the Dockerfile/Flask CLI points at (`app.main`). Don't build the Flask `app` object at import time outside the factory — extensions are created empty in `backend/app/extensions.py` (`db = SQLAlchemy()`, `migrate = Migrate()`, `cors = CORS()`) and only bound to the real app inside `create_app()` via `db.init_app(app)`. This split exists so `models.py` can `from app.extensions import db` without needing a live app instance yet.

**Config.** `backend/app/config.py` uses `pydantic-settings` (`Settings`) to read `DATABASE_URL`, `ANTHROPIC_API_KEY`, and `SOCRATA_APP_TOKEN` from `.env`. This is the only place environment variables should be read — don't call `os.environ` directly elsewhere.

**Sync stack, deliberately.** This project intentionally uses Flask + Flask-SQLAlchemy + Flask-Migrate (sync/WSGI), not FastAPI + Tortoise (async/ASGI) — that swap already happened once (see git history) after weighing async-vs-sync tradeoffs for this project's scale. Don't reintroduce `async def` routes or an async ORM without an explicit decision to revisit that tradeoff.

**Schema design intent.** The `complaints` table (`backend/app/models.py`) mirrors NYC's Socrata 311 dataset. Key decisions baked into it:
- `unique_key` is the primary key and is **not** auto-generated (`autoincrement=False`) — it's Socrata's own ID, so ingestion can safely upsert (`ON CONFLICT` / merge) instead of creating duplicates on re-runs.
- The three indexes (`created_date` alone, `(borough, created_date)`, `(complaint_type, created_date)`) exist specifically to match the filter shape `/api/complaints` and `/api/ask` both use: borough + complaint_type + date range. Don't add unrelated indexes without a query pattern driving them.
- `borough` is a Python `str, enum.Enum` (`Borough`) mapped via SQLAlchemy's `Enum` with `native_enum=False` (stored as `VARCHAR`, not a Postgres native enum type) and `create_constraint=True`, which generates a real Postgres `CHECK` constraint — invalid values are rejected by the database itself, not just validated in Python. It also uses `values_callable` so the stored value is the enum's `.value` ("STATEN ISLAND", with a space) rather than its `.name` ("STATEN_ISLAND") — get this wrong and inserted data silently won't match what ingestion normalizes to.

**Ingestion (`backend/scripts/ingest_311.py`).** Standalone script, not part of the request path — pulls the last `MONTHS_BACK` months from Socrata dataset `erm2-nwe9` and upserts into `complaints`. Notable, non-obvious things about it:
- `unique_key` is typed as **Text** in Socrata's own schema, not Number — comparing it unquoted in `$where` fails with a live `query.soql.type-mismatch` error. Keyset pagination (not offset — Socrata's own docs warn offset degrades past tens of thousands of rows) therefore compares and orders it as a string, which is only correct because all `unique_key` values in a short recent window share the same digit count.
- Socrata's timestamps are naive local `America/New_York` time, not UTC — `parse_socrata_datetime` localizes them before storing, so `created_date` in Postgres is always a proper UTC-aware `TIMESTAMPTZ`.
- `fetch_page` retries transient network errors (`httpx.TransportError`) with backoff; HTTP error responses (4xx/5xx) are not retried, since retrying a malformed request would never succeed.
- `run()` persists `{since, last_unique_key}` to a local, gitignored checkpoint file after every page and clears it on completion — an interrupted run resumes from where it left off instead of re-pulling the whole window.

**API routes (`backend/app/routes.py`).** A Flask Blueprint (`api_bp`, prefixed `/api`), registered in `create_app()` — not routes defined inline there, since more than a trivial number of endpoints deserves its own module. `GET /api/complaints` (filtered, paginated list), `GET /api/complaints/summary` (`GROUP BY complaint_type`), `GET /api/complaints/points` (lat/long + type only, capped at `MAX_POINTS_LIMIT`, for the map view's heatmap/cluster modes), and `GET /api/complaints/<unique_key>` (a single full record, for the map view's click-to-inspect popup) share filter-building logic via `apply_borough_and_date_filters()` (except the single-record lookup, which doesn't filter). Date query params (`start`/`end`) are parsed as **NYC-local calendar days**, matching the same `America/New_York` convention the ingestion script uses — a query for `start=2026-05-01` and stored data both mean the same instant, even though neither is naive UTC midnight.

**CORS.** Scoped to `/api/*` and explicitly to the Vite dev origins (`localhost:5173` / `127.0.0.1:5173`) in `create_app()` — not wildcarded. Revisit this scoping when there's an actual deployed frontend origin to allow.

**`POST /api/ask` (`backend/app/routes.py`).** Claude does NL→structured-filter via forced tool use (`extract_complaint_filter`), never raw SQL generation and never direct DB access. Two sequential `messages.create` calls, both with `thinking={"type": "disabled"}` since structured extraction and short summarization don't need deep reasoning: the first is forced to call the tool (`tool_choice={"type": "tool", ...}`) and returns a filter dict plus a `mode` of `"summary"` or `"list"` that Claude itself decides based on the question's phrasing — not hardcoded. That filter dict is passed straight into `apply_borough_and_date_filters()` (the same function `/api/complaints` uses, refactored to accept either `request.args` or a plain dict, since both support `.get(key)`), the backend runs the real query, and the results are sent back to Claude in a second call (assistant turn = the first response's `content`, followed by a `tool_result` user turn) to produce a plain-English answer. Neighborhood names (e.g. "Bushwick") are mapped to boroughs by Claude's own general knowledge — the schema only has borough-level granularity, so this is intentional, not a gap. Rate-limited to 10 requests/hour per IP via Flask-Limiter (`backend/app/extensions.py`), since this repo is public and the Anthropic API key is billed separately from a claude.ai subscription — don't remove the rate limit without another cost-abuse mitigation in place. Model is pinned to `claude-sonnet-5` (not the more capable default) as an explicit cost tradeoff for a pet project.

**Frontend (`frontend/`).** Vue 3 + Vite, plain `fetch()` (`src/api.js`), no state management library, no chart library — deliberately thin. `App.vue` renders nothing but `MapView.vue` — the map is the whole app, not one section of a page. `ComplaintsTable.vue` implements infinite scroll without `IntersectionObserver`: a reactive ref tracks scroll position, and the near-bottom check is done fresh inside the `watch()` callback rather than gating on a derived boolean's change — a boolean that stays `true` across several consecutive scroll events (e.g. a user resting near the bottom) won't retrigger `watch()`, since Vue only fires on an actual value change, which silently drops every load after the first. It takes an optional `scrollContainer` prop (an element, defaulting to `window`) since `MapView.vue` embeds it inside its own scrollable overlay panel rather than the page body; that prop is watched with `{ immediate: true }` rather than read once in `onMounted`, since the panel's template ref can still be `null` at the table's own mount time — the reactive watch self-corrects once the parent's ref resolves instead of silently listening on the wrong target forever. `AskBox.vue` is a plain text input + submit that POSTs to `/api/ask` and renders the returned `answer` string — it doesn't share state with `FilterBar`/`ComplaintsTable`, since the two querying modes (structured filters vs. NL question) are deliberately independent.

**Theming.** `src/style.css` defines the full color palette as CSS variables twice: once on bare `:root` (light, the default) and again under both `@media (prefers-color-scheme: dark) { :root:not([data-theme='light']) {...} }` and `:root[data-theme='dark'] {...}` — the two dark blocks exist so an explicit choice (via the toggle) always wins over the OS setting, in either direction. `useTheme.js` (`src/composables/`) tracks the *effective* theme (`localStorage` override, falling back to `matchMedia('(prefers-color-scheme: dark)')`, kept in sync via that query's `change` event) rather than just the stored override — get this wrong (as the first version of this composable did) and `ThemeToggle.vue`'s icon shows "switch to dark" while the page is already dark because the OS, not the user, put it there. `index.html` has a small inline script that applies a stored override before Vue mounts, so a returning user with an explicit choice never sees a flash of the other theme. `--heat-1` through `--heat-4` are a separate sequential scale (cool → hot) for map data encoding — deliberately not derived from `--accent`, since a single-hue alpha ramp reads poorly for density/magnitude data.

**Map view (`MapView.vue`).** The map is a fixed, edge-to-edge `position: fixed; inset: 0` shell — not a card in a page — with two floating overlay panels rather than a page laid out around the map. The left panel nests `AskBox`, `FilterBar`, `TopComplaintTypes`, and `ComplaintsTable` (all sharing one `overflow-y: auto` scroll region, which is what `ComplaintsTable`'s `scrollContainer` prop is for); the right panel holds the mode switcher and legend. `FilterBar`'s `change` event bubbles up through `MapView`'s own `filters-change` emit to `App.vue`, which still owns the `filters` state — `FilterBar` moved into `MapView`'s template, not its state ownership. `NavigationControl` is added at `bottom-right`, not MapLibre's default corner, since the right overlay panel occupies top-right; there's no separate `AttributionControl` either, since the panel's own "Basemap © OpenStreetMap..." text already satisfies the attribution requirement.

MapLibre GL JS + free vector tiles from [OpenFreeMap](https://openfreemap.org) (`tiles.openfreemap.org/styles/liberty` light / `.../dark` dark, switched via `useTheme()`), with a tab switcher between two modes sharing one map instance and one `points` GeoJSON source built from `/api/complaints/points`: `heatmap` (a `type: 'heatmap'` layer) and `clusters` (MapLibre's built-in `cluster: true` clustering on a second `points-clustered` source over the same data — a separate source because a source can't be both clustered and un-clustered at once). Both respect the same `filters` prop as `FilterBar`/`ComplaintsTable`. Clicking an unclustered point (visible once you've zoomed a cluster apart) fetches that one complaint from `GET /api/complaints/<unique_key>` and shows it in a `maplibregl.Popup` — a separate lazy fetch rather than putting `descriptor`/`status`/dates on every point up front, since `/api/complaints/points` is deliberately kept light for payloads of up to `MAX_POINTS_LIMIT` rows. `frontend/vite.config.js` excludes `maplibre-gl` from `optimizeDeps` — MapLibre spawns a Web Worker for tile/GeoJSON processing via a relative `new URL(..., import.meta.url)`, and Vite's esbuild dependency pre-bundler doesn't preserve that as a separately fetchable chunk in dev mode, so the worker silently 404s and every GeoJSON-sourced layer never renders (no thrown error — sources report empty feature data). Import it as `import * as maplibregl from 'maplibre-gl'`, not a default import — the package has no default export, only named ones (`Map`, `Popup`, `NavigationControl`, ...). When updating a GeoJSON source after an async fetch, call `getSource(id)?.setData(...)` unconditionally rather than gating on `map.isStyleLoaded()` — that can stay `false` well after the source already exists and safely accepts updates, and gating on it silently drops the update.

## Code style

No narrative comments — nothing that reads like a debugging log or tells the story of how a bug was found ("confirmed by hitting the live API", "this used to fail because..."). A comment should state a fact or a non-obvious constraint as if it were always true, not narrate the process that led to it. Prefer no comment at all unless the WHY genuinely isn't obvious from the code.

Architecture-level rationale (why a dependency is configured a certain way, why a whole component is shaped the way it is, cross-file constraints) belongs in this file, not inline — this file is the durable reference for it, so it should exist in exactly one place rather than duplicated between a comment block and here. Inline comments stay short: enough to flag that a specific line has a non-obvious reason, without re-deriving the reason on the spot — point at this file for the full explanation instead of repeating it.
