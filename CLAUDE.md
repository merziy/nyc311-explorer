# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

NYC 311 Explorer: a "chat with your data" app over NYC's 311 service request dataset. A Flask API backed by Postgres (`backend/`), an ingestion script that pulls real data from NYC's Socrata API, and a Vue 3 frontend (`frontend/`) all exist and work end to end. The `/api/ask` NL→filter endpoint (Claude tool-use) does not exist yet — that's the next major piece.

## Commands

Local Postgres (dev):
```
docker compose up -d
```
Starts Postgres 16 on `localhost:5432` with user/password/db all `nyc311` (see `docker-compose.yml`).

Backend setup:
```
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp ../.env.example .env   # then fill in ANTHROPIC_API_KEY and SOCRATA_APP_TOKEN
```
`DATABASE_URL` in `.env.example` already matches the docker-compose credentials. `SOCRATA_APP_TOKEN` comes from a free account at data.cityofnewyork.us (Profile → Developer Settings, or the API panel on the dataset's own page) — ingestion works without one but at a much lower rate limit.

Run the backend:
```
cd backend
FLASK_APP=app.main .venv/bin/flask run --port 8000
```

Run the frontend (separate terminal):
```
cd frontend
npm install
npm run dev
```
Opens on `http://localhost:5173`. The backend must be running on `:8000` — CORS is only opened for that specific origin (see Architecture below), not wildcarded.

Migrations (Flask-Migrate / Alembic, config lives in `backend/migrations/`):
```
cd backend
FLASK_APP=app.main .venv/bin/flask db migrate -m "description"   # autogenerate from models.py
FLASK_APP=app.main .venv/bin/flask db upgrade                    # apply
FLASK_APP=app.main .venv/bin/flask db downgrade                  # roll back one revision
```
Always read the autogenerated migration in `backend/migrations/versions/` before applying it — Alembic's autogenerate misses some things (e.g. it won't infer `CHECK` constraints unless the model explicitly declares them, as `models.py` does for `borough`).

Ingestion (pulls real 311 data from Socrata into `complaints`):
```
cd backend
.venv/bin/python -m scripts.ingest_311
```
Safe to re-run or interrupt — see Architecture below for the checkpoint/retry behavior.

No test suite, linter, or CI config exists yet.

## Architecture

**App factory pattern.** `backend/app/__init__.py` defines `create_app()`, which builds and configures the Flask app; `backend/app/main.py` just calls it (`app = create_app()`) and is the entrypoint the Dockerfile/Flask CLI points at (`app.main`). Don't build the Flask `app` object at import time outside the factory — extensions are created empty in `backend/app/extensions.py` (`db = SQLAlchemy()`, `migrate = Migrate()`, `cors = CORS()`) and only bound to the real app inside `create_app()` via `db.init_app(app)`. This split exists so `models.py` can `from app.extensions import db` without needing a live app instance yet.

**Config.** `backend/app/config.py` uses `pydantic-settings` (`Settings`) to read `DATABASE_URL`, `ANTHROPIC_API_KEY`, and `SOCRATA_APP_TOKEN` from `.env`. This is the only place environment variables should be read — don't call `os.environ` directly elsewhere.

**Sync stack, deliberately.** This project intentionally uses Flask + Flask-SQLAlchemy + Flask-Migrate (sync/WSGI), not FastAPI + Tortoise (async/ASGI) — that swap already happened once (see git history) after weighing async-vs-sync tradeoffs for this project's scale. Don't reintroduce `async def` routes or an async ORM without an explicit decision to revisit that tradeoff.

**Schema design intent.** The `complaints` table (`backend/app/models.py`) mirrors NYC's Socrata 311 dataset. Key decisions baked into it:
- `unique_key` is the primary key and is **not** auto-generated (`autoincrement=False`) — it's Socrata's own ID, so ingestion can safely upsert (`ON CONFLICT` / merge) instead of creating duplicates on re-runs.
- The three indexes (`created_date` alone, `(borough, created_date)`, `(complaint_type, created_date)`) exist specifically to match the filter shape `/api/complaints` and the planned `/api/ask` endpoint use: borough + complaint_type + date range. Don't add unrelated indexes without a query pattern driving them.
- `borough` is a Python `str, enum.Enum` (`Borough`) mapped via SQLAlchemy's `Enum` with `native_enum=False` (stored as `VARCHAR`, not a Postgres native enum type) and `create_constraint=True`, which generates a real Postgres `CHECK` constraint — invalid values are rejected by the database itself, not just validated in Python. It also uses `values_callable` so the stored value is the enum's `.value` ("STATEN ISLAND", with a space) rather than its `.name` ("STATEN_ISLAND") — get this wrong and inserted data silently won't match what ingestion normalizes to.

**Ingestion (`backend/scripts/ingest_311.py`).** Standalone script, not part of the request path — pulls the last `MONTHS_BACK` months from Socrata dataset `erm2-nwe9` and upserts into `complaints`. Notable, non-obvious things about it:
- `unique_key` is typed as **Text** in Socrata's own schema, not Number — comparing it unquoted in `$where` fails with a live `query.soql.type-mismatch` error. Keyset pagination (not offset — Socrata's own docs warn offset degrades past tens of thousands of rows) therefore compares and orders it as a string, which is only correct because all `unique_key` values in a short recent window share the same digit count.
- Socrata's timestamps are naive local `America/New_York` time, not UTC — `parse_socrata_datetime` localizes them before storing, so `created_date` in Postgres is always a proper UTC-aware `TIMESTAMPTZ`.
- `fetch_page` retries transient network errors (`httpx.TransportError`) with backoff; HTTP error responses (4xx/5xx) are not retried, since retrying a malformed request would never succeed.
- `run()` persists `{since, last_unique_key}` to a local, gitignored checkpoint file after every page and clears it on completion — an interrupted run resumes from where it left off instead of re-pulling the whole window.

**API routes (`backend/app/routes.py`).** A Flask Blueprint (`api_bp`, prefixed `/api`), registered in `create_app()` — not routes defined inline there, since more than a trivial number of endpoints deserves its own module. `GET /api/complaints` (filtered, paginated list) and `GET /api/complaints/summary` (`GROUP BY complaint_type`, same borough/date filters) share filter-building logic via `apply_borough_and_date_filters()`. Date query params (`start`/`end`) are parsed as **NYC-local calendar days**, matching the same `America/New_York` convention the ingestion script uses — a query for `start=2026-05-01` and stored data both mean the same instant, even though neither is naive UTC midnight.

**CORS.** Scoped to `/api/*` and explicitly to the Vite dev origins (`localhost:5173` / `127.0.0.1:5173`) in `create_app()` — not wildcarded. Revisit this scoping when there's an actual deployed frontend origin to allow.

**Frontend (`frontend/`).** Vue 3 + Vite, plain `fetch()` (`src/api.js`), no state management library, no chart library — deliberately thin. `ComplaintsTable.vue` implements infinite scroll without `IntersectionObserver`: a reactive ref tracks scroll position, and the near-bottom check is done fresh inside the `watch()` callback rather than gating on a derived boolean's change — a boolean that stays `true` across several consecutive scroll events (e.g. a user resting near the bottom) won't retrigger `watch()`, since Vue only fires on an actual value change, which silently drops every load after the first.

**Planned but not yet built**: a `/api/ask` endpoint where Claude does NL→structured-filter (tool-use, not raw SQL generation) against the same filter shape `/api/complaints` already accepts, and structured-results→English summary; a map/heatmap view (deliberately not scoped yet — needs its own design pass on shading metric and mapping library); Dockerfiles wired into an actual deployment (backend's Dockerfile exists but is unused so far).

## Code style

No narrative comments — nothing that reads like a debugging log or tells the story of how a bug was found ("confirmed by hitting the live API", "this used to fail because..."). A comment should state a fact or a non-obvious constraint as if it were always true, not narrate the process that led to it. Prefer no comment at all unless the WHY genuinely isn't obvious from the code.
