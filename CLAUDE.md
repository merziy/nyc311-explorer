# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

NYC 311 Explorer: a "chat with your data" app over NYC's 311 service request dataset. Only the backend (`backend/`) exists so far — a Flask API backed by Postgres. No ingestion script, no `/api/ask` endpoint, and no frontend have been built yet.

## Commands

Local Postgres (dev):
```
docker compose up -d
```
Starts Postgres 16 on `localhost:5432` with user/password/db all `nyc311` (see `docker-compose.yml`).

Backend setup:
```
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp ../.env.example .env   # then fill in ANTHROPIC_API_KEY if needed
```
`DATABASE_URL` in `.env.example` already matches the docker-compose credentials.

Run the app:
```
cd backend
FLASK_APP=app.main .venv/bin/flask run --port 8000
```
`GET /health` is the only route so far.

Migrations (Flask-Migrate / Alembic, config lives in `backend/migrations/`):
```
cd backend
FLASK_APP=app.main .venv/bin/flask db migrate -m "description"   # autogenerate from models.py
FLASK_APP=app.main .venv/bin/flask db upgrade                    # apply
FLASK_APP=app.main .venv/bin/flask db downgrade                  # roll back one revision
```
Always read the autogenerated migration in `backend/migrations/versions/` before applying it — Alembic's autogenerate misses some things (e.g. it won't infer `CHECK` constraints unless the model explicitly declares them, as `models.py` does for `borough`).

No test suite, linter, or CI config exists yet.

## Architecture

**App factory pattern.** `backend/app/__init__.py` defines `create_app()`, which builds and configures the Flask app; `backend/app/main.py` just calls it (`app = create_app()`) and is the entrypoint the Dockerfile/Flask CLI points at (`app.main`). Don't build the Flask `app` object at import time outside the factory — extensions are created empty in `backend/app/extensions.py` (`db = SQLAlchemy()`, `migrate = Migrate()`) and only bound to the real app inside `create_app()` via `db.init_app(app)`. This split exists so `models.py` can `from app.extensions import db` without needing a live app instance yet.

**Config.** `backend/app/config.py` uses `pydantic-settings` (`Settings`) to read `DATABASE_URL` and `ANTHROPIC_API_KEY` from `.env`. This is the only place environment variables should be read — don't call `os.environ` directly elsewhere.

**Sync stack, deliberately.** This project intentionally uses Flask + Flask-SQLAlchemy + Flask-Migrate (sync/WSGI), not FastAPI + Tortoise (async/ASGI) — that swap already happened once (see git history) after weighing async-vs-sync tradeoffs for this project's scale. Don't reintroduce `async def` routes or an async ORM without an explicit decision to revisit that tradeoff.

**Schema design intent.** The `complaints` table (`backend/app/models.py`) mirrors NYC's Socrata 311 dataset. Key decisions baked into it:
- `unique_key` is the primary key and is **not** auto-generated (`autoincrement=False`) — it's Socrata's own ID, so ingestion can safely upsert (`ON CONFLICT` / merge) instead of creating duplicates on re-runs.
- The three indexes (`created_date` alone, `(borough, created_date)`, `(complaint_type, created_date)`) exist specifically to match the filter shape a planned `/api/ask` endpoint will use: borough + complaint_type + date range. Don't add unrelated indexes without a query pattern driving them.
- `borough` is a Python `str, enum.Enum` (`Borough`) mapped via SQLAlchemy's `Enum` with `native_enum=False` (stored as `VARCHAR`, not a Postgres native enum type) and `create_constraint=True`, which generates a real Postgres `CHECK` constraint — invalid values are rejected by the database itself, not just validated in Python. It also uses `values_callable` so the stored value is the enum's `.value` ("STATEN ISLAND", with a space) rather than its `.name` ("STATEN_ISLAND") — get this wrong and inserted data silently won't match what ingestion normalizes to.

**Planned but not yet built** (referenced here so schema decisions above make sense): a standalone ingestion script pulling from NYC's Socrata API and upserting into `complaints`; a `/api/ask` endpoint where Claude does NL→structured-filter (tool-use, not raw SQL generation) and structured-results→English summary, running against a parameterized query the backend controls; a Vue 3 + Vite frontend.

## Code style

No narrative comments — nothing that reads like a debugging log or tells the story of how a bug was found ("confirmed by hitting the live API", "this used to fail because..."). A comment should state a fact or a non-obvious constraint as if it were always true, not narrate the process that led to it. Prefer no comment at all unless the WHY genuinely isn't obvious from the code.

## Git conventions
